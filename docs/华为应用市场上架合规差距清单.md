## 4. 核心矛盾：产品形态与商店审核模型的冲突

这是本次审计最需要你做决策的地方，其他问题都是补文件，这一条是补文件解决不了的。

**现状**：应用把「热量估算」这一唯一核心功能，完全外包给用户自己配置的 LLM。程序本身不含任何食物库、MET 表或本地估算能力（`README.md:3`、`项目描述.md:11` 明确为设计哲学）。

**与审核模型的冲突**：

- 审核员拿到的 APK **开箱即空**：不填 Key，四类 AI 任务全部不可用，界面没有任何数据。
- 要求用户自备**付费第三方 API Key** 才能使用主功能，商店通常认定为「功能不完整」或「变相让用户承担费用」。
- 隐私政策必须说明数据发给第三方；若用户填的是境外接口，还触发个人信息出境合规。
- README 自己也承认「定位为功能完整的个人工具，**非上架商品**」（`项目描述.md:77`），"自签名应用，不是应用商店版本"（`android/README-Android.md:259`）。

**可选的破解路径（按可行性排序）**：

| 方案 | 做法 | 代价 | 可行性 |
|---|---|---|---|
| A（推荐） | 内置**离线估算兜底**：内置一份精简食物库 + MET 表，无 Key 时也可完成记录与热量差计算；LLM 降级为「增强项」 | 违背现有设计哲学，需新增数据与估算模块 | 高。这样审核员开箱即用，AI 成为加分项而非门槛 |
| B | 申请一个**官方托管 Key**（或自建后端代理）供审核与免费额度使用，明确用量上限与隐私边界 | 产生持续费用；自建后端后**必须做 ICP 备案**，合规成本显著上升 | 中 |
| C | 提供**演示模式**：无 Key 时加载示例数据 + 明确标注「演示数据」，并把部署 Key 的指引放到显著位置 | 审核可能仍判「功能不完整」 | 中低 |
| D | 改为**面向企业/侧载分发**，不上 AppGallery；或改投对开发者工具更宽容的渠道 | 失去商店分发 | 视目标而定 |

> 若坚持不改产品形态，**个人开发者 + 健康类目 + 需自备付费 Key**，三项叠加几乎必然驳回。建议先按第 3 节第 1、3 项确认主体与备案资格，再决定是否投入整改。
